# 站位与调度方法（blockingPlans 作者侧）

本资源随 `tapcanvas-dramatic-adapter` 骨架自动注入。它回答**站位怎么决定**，不是站位图怎么画（绘制范式见 `tapcanvas-scene-card/references/topology-blocking-diagram.md`），也不是字段怎么填（结构纪律见主文档 `blockingPlans[]`）。

## 站位图为什么会"画得出来、读不出戏"

站位图要让下游在**不知道剧情**的情况下只读坐标就把机位放对、把人物接上。失效方式很安静：每个 `[x,y]` 都合法，`characters[]` 也精确覆盖 `objectStates`，结构校验全绿，但图只说明"有人站在几个点上"——没人能说出谁在挡谁、谁在施压、镜头为什么在这、上一拍的位置关系有没有延续。

根因是作者在**填坐标**而不是在**做调度决定**。调度决定只有四个，其余都是推论：

```text
谁能看见、接近、挡住什么   -> 位置
此刻谁大于谁              -> 机位高度与距离
观众被允许读到谁的表情     -> 水平角度与朝向
这一拍在轴线哪一侧继续     -> 侧位继承
```

先答这四问，坐标自然落下；先挑坐标再编理由，会产出合格的站位图和不合格的调度。

## 规则分级

- `structural_invariant`：坐标范围、角色覆盖、时长一致、索引对齐。宿主确定性校验，不合格直接拒。
- `reviewed_invariant`：轴线可继承、视线方向互补、本拍必须被读到的信息有可见载体。作者冻结前自行比较，不合格必须改，不能留给下游猜。
- `craft_default`：先建立地理再切近、让空间承载压力、用纵深换横向。有明确戏剧理由时由作者说明并覆盖。
- `taste_option`：机位高度风格、构图留白、是否用前景遮挡。由本轮视觉方向决定，不因偏离本文示例判错。

## 一、俯视坐标与画面左右是两套读数

**`structural_invariant`**：`[x,y]` 是**平面坐标**（原点左上，x 向右，y 向下），描述人物在空间平面上的位置。**画面左右是观众看到的左右**，只在机位确定之后才存在。两者混用是站位图最常见的失效来源。

- 裸写的"左/右"一律指**画面左右**；指人物自身必须带主体（"他的左手""她的右肩"）。
- 指平面位置时用坐标或"平面 x 较大侧"，不能写"左边"。

判据：只读这一拍的 `camera` 与 `characters[].at`，能否独立推出"谁在画面左"。推不出来说明调度没有确定，坐标只是装饰。

`focalPoint`、`centerPlacement` 是**画幅级**字段，相对机位取景框定义；`characters[].at` 是**平面级**字段。同一对象的 `at` 与 `centerPlacement` 必须由同一台机位和解出来，不能各写一套。

## 二、轴线是两个可命名锚点的连线

**`structural_invariant`**：`axisLine` 不是形容词，是**两个可命名锚点的连线**。判据是换一个没读过剧本的人来拍下一拍，只读这三行就能把机位放对：

```text
axisLine: 甲 ↔ 乙（锚点是稳定对象名或地标名）
working side: 机位常驻哪一侧（用平面方位或地标描述）
屏幕方向: 甲固定占画面左，乙固定占画面右（机位与轴线关系确定后才成立）
```

写成"两人之间""侧面"等于没写。锚点优先取**本拍已登记且跨拍稳定**的对象：主对角两人、被争夺的关键道具、地标。单人对环境的镜头，轴线取"人物 ↔ 人物正在看或接近的地标"。

轴线服务于"谁能看见谁"，不服务于构图美观。选错的症状：观众看不清谁在看谁，正反打一切换方向就反了，阻断或监视关系读不出来。

## 三、working side 继承与越轴记账

同一场景连续多拍，`camera.at` 必须落在轴线的哪一侧由首拍决定，这个侧位是**跨拍继承的事实**：

- 轴线锚点未变时，后续拍的 `camera.at` 必须与首拍同侧。位置可沿轴线移动、可远近变化，但不能跳到对侧。
- 越轴只有三种合法来源：插入中性过渡拍（机位落在轴线上或正对轴线）、本拍内让人物穿过轴线并把该动作写进 `storyEvents`、或明确重新建立空间（新场景、新时段、新拍摄段落）。
- 越轴那一拍**必须自己写明依据**（写进 `camera`、`title` 或 `narrativeTask`），不能让下游从方向矛盾里反推；越轴之后必须重新声明新的 working side 并让后续拍继承。
- 同场景换轴线锚点（如从"甲↔乙"换成"甲↔柜台"）是合法的重新安放，同样要写明依据：谁的位置或目标变了。

否则每一拍都在各自猜轴线在哪，观众读到的是空间崩坏。

## 四、正反打配对

`relationship` 或 `character` 焦点的对话拍成对出现时逐项核对：

- **屏幕方向互补**：A 拍里甲占画面左看向右，B 拍里乙就必须占画面右看向左。两拍都望向同一侧时，观众读到的不是对话，是两人在看同一个画外的第三者。
- **视线高度按实际身高差匹配**：一方明显高时，A 拍的低机位与 B 拍的高机位要对应。两拍都平视会把身高差抹平，也让"逼近"失去压迫感。
- **过肩拍写明前景是谁的肩、占画多少**：前景肩的归属决定这一拍属于谁的视角。
- **A/B 是否对称是主动选择**：机位高度与景别对称表示势均力敌，不对称表示权力倾斜；选了不对称就在 `narrativeTask` 写出理由。

## 五、竖屏用纵深换横向

9:16 的横向可用宽度只有 16:9 的三分之一强。横向铺开的信息（谁站在谁旁边、队列多长、离出口多远）在竖屏里要么挤成一条，要么小到读不出。竖屏调度不是把横屏排法裁窄，而是**把关系从横向搬进纵深**：

- 用前景、中景、后景分层，靠 `subjects[].depthLayer` 明确表态，别让所有人落在同一层。
- 用门框、桌沿、台阶、人的前后遮挡立关系；遮挡要承担信息（谁被挡住＝谁此刻不占优势），不承担信息的前景遮挡是噪音。
- 明确谁能接近证据、出口或权力座位。空间优势在竖屏里通常由"更靠前"表达，而不是"更靠边"。
- 头像高低只在空间真实且有意义时表达地位；要用高度表达权力之前，先看水平角度和前后层能不能承担。
- 两人对话时仍要保留第三人的监听、反应或阻挡位置；把人塞出画面等于丢掉一条关系线。

做到了纵深层次，竖屏一样可以给 `establishing` / `wide`；做不到就不要用这两档承担交代空间的职责。

## 六、关系投影：多人镜先画关系再摆人

**`reviewed_invariant`**：多人对峙、群体压迫、家庭冲突这类场面，先写一张**有方向的关系投影**——谁此刻保护谁、与谁协作、向谁施压、在观察谁，这条关系由哪个剧本动作或信息状态支持——再翻成 `at` 位置、`facingTo` 朝向、可见距离和必要的 `moveTo` 行动线。

一帧内不能既与甲背靠背结盟、又从对立行动线朝甲施压。同一人物可以在剧情转向后换边，但一个拍里只能有一个立场。逐项核对人物、手持物和阵营，避免同一角色被写进两个互斥位置。

群体不要按人建轴，按作用分区：主行动者与对手的**主要轴线**（一条）；见证者或队列所在**区域**；入口、出口与权力位置；群体注意方向的变化。公开揭示或家庭冲突中，再按行动能力区分知情者、能作决定的人、利益相关者和普通旁观者；只有新事实改变某组人能做什么时，才给这组人新的动作。

多人场面最先崩掉的通常不是冲突，是**辨识**。竖屏观众没有回看的习惯，错过一次就一路错下去。可用手段按代价从低到高：减人（与本拍议程无关的人不出现）、让人陆续进场、分段轮换主对手（每段只让一个人真正与焦点人物交手）、人物之间明确递交（切换注意力前先由当前说话者点名或看向下一个人）。该不在场的人不要出现在 `characters[]` 里。

## 七、动态对象的控制权交接

**`reviewed_invariant`**：球、车辆、武器、证物、接力物或争夺中的工具会把控制权和空间关系带过切拍。先写清当前时间或回合、区域、控制者、运动方向、目标路线、可用反制；不适用就省略，不为填表虚构数据。

一次关键行动至少要让观众理解：动作从什么可见状态开始、控制权怎样被争夺或转移、方向或战术为何改变、结束时对象与人物分别在哪。

- 切拍后动态对象应从上一拍结束的位置和方向继续，除非明确跳时或省略。`moveTo` 只表达本拍内位移，跨拍连续性由上一拍退出态承接。
- 只有改变选择时才进入画面的比分、计时和阵形；精确文字不可靠呈现时标记为后期图形或声音信息，不让关键帧提示词临时造字。
- 对手的战术调整应能追溯到此前看见的信息，避免每拍重置成同一站位。
- 反应镜只在接收者的新判断会改变下一动作时承担职责，不能用欢呼遮住控制权转移。

## 八、机位、视角与景别

`camera.at` 与 `camera.lookAt` 共同定义视锥。逐项确认：

- **位置合法**：机位不能落在墙里、家具里或人物身上，必须与 `landmarks[]` 声明的空间事实相容。
- **视线可达**：`lookAt` 与 `focalPoint` 指向同一注意力中心；本拍必须被读到的东西（脸、证据文字、决定性的手部动作）在视锥内且不被前景层挡死。
- **水平角度与机位高度分开写**：水平角度（正面／斜侧／正侧／后斜侧／背面）回答"观众被允许读到多少表情、站在谁的一侧"；机位高度回答"谁在这一刻大于谁"。写"俯拍"时想表达的若是"从她背后越过肩膀"，那是水平角度不是高度，下游按字面给一个从上往下的机位会让权力关系当场反转。
- **不无限增机位**：一场真实需要的机位数量由注意力变化决定；把两台机位硬套给全部场景，和每拍换一个机位，是同一种失真。
- **相机运动轨迹**当前工具只支持静态机位；需要跟随、甩镜、绕行时，在 `narrativeTask` 或下游正文里写清运动理由与目标，不在站位图字段里假装支持。

`shotScale` 不是情绪音量旋钮。判断标准始终是**必须被读到的信息存在于哪个尺度**：证据在指节上就给 `close`／`detail`，后果在两人距离上就不该切近。

- 一场通常比它真正要演的景别**先开宽一档**，第二拍落到本场的**工作景别**，之后多数切拍在这一档上下一格来回。
- `establishing` / `wide` 与 `close` / `detail` 是**离开工作景别的标记事件**，用过就回来；场尾略微放开是常见收法。一路单调收紧的场次到中段就没有余量了。
- 一旦决定切拍，新拍必须在景别、机位角度或人物关系里至少改变一项。三项都没变时观众读到的不是节奏，是跳切或穿帮。
- 不切拍本身也是选择：压力累积、人物在同一构图里自己改变距离、观众被迫看着不肯变的画面，都是有效理由。

## 九、交付面遮挡

竖屏画幅在播放时通常不是完整可见的：播放界面会叠字幕条、控件、进度条、侧边互动控件、角标。**画幅是满的，可读区不是。**

这条只在创作者已声明交付面遮挡区时生效；没有声明就保持未解决，照常按画面本身的可读性构图，**不因为猜测的区域改变构图**。声明存在时按优先级判断哪些内容必须挪开：

- **可读文字最敏感**：证据类道具上必须被读出的字一旦落在字幕条位置，观众永远读不到。要么挪到中部可读区，要么改用更近的景别单独给一次。
- **脸与眼神次之**：竖屏习惯把人物放得很高，容易压到顶部角标区。不要为避让把所有人一律推到正中，那会让全片构图变平。
- **一侧的互动控件**是竖屏特有的：关键动作落在被占用的那一侧时，把动作调到另一侧或用镜像的机位关系解决，**不要靠缩小主体来避让**。

失效方式是安静的：单帧看构图很好，放到实际播放面才发现关键信息被压住，而此时关键帧与视频提示词都已经做完了。这个判断属于站位与构图阶段。

## 十、字段落点

每个调度决定只有一个落点，不在多处重复表达同一事实：

| 调度决定 | 落点 |
|---|---|
| 谁在哪、谁挡住什么、能不能接近 | `characters[].at`、`landmarks[]` |
| 谁朝向谁、视线方向 | `characters[].facingTo` |
| 本拍内位移与行动线 | `characters[].moveTo` |
| 戏剧轴线与可命名锚点 | `axisLine.from/to` |
| 机位侧位、视线中心、越轴依据 | `camera.at/lookAt` + `narrativeTask` |
| 观众此刻必须读到什么 | `focusKind`、`focusTargetNames`、`focalPoint` |
| 谁是主读对象、谁退出注意 | `subjects[].visualWeight` |
| 前中后景分层 | `subjects[].depthLayer` |
| 是否允许落在画面中心 | `subjects[].centerPlacement` |
| 在画幅里占多高 | `subjects[].maxFrameHeightRatio` |
| 观察尺度与工作景别 | `shotScale` |
| 环境在画面里占多大话语权 | `environmentVisualWeight` |
| 空镜或无人物拍的空间表达 | `landmarks[]` + `camera` |

底图（`backgroundPlan`）只承载**无人、正交俯视、与本拍坐标一致**的空间；人物、箭头、机位、文字标签由宿主按原坐标叠画。不要为了"让图好看"把人物画进底图提示词，也不要因为要写人物就省略结构化站位。

## 十一、冻结前自检

逐拍回答，任何一条答不出就回改本拍：

1. 只读 `camera` 与 `characters[].at`，能否独立推出画面左右？三个及以上人物时，能否推出谁在谁的前后？
2. `axisLine` 的两个锚点是否可命名、是否跨拍稳定？本拍机位在轴线哪一侧，与同场景上一拍是否同侧？越轴是否在本拍写明依据？
3. 本拍必须被读到的信息在哪个 `depthLayer`、占多高、是否被前景挡死？
4. `facingTo` 是否表达"谁在看谁"？正反打两侧的屏幕方向是否互补？
5. `moveTo` 的对象在上一拍退出态里确实处在起点位置吗？本拍结束位置是否被下一拍接住？
6. 每个人物能否在当前空间里合理站立、看见和移动？有没有人站在墙里、挡死出口却不承担信息、或被前景无理由遮住？
7. `shotScale` 能否回答"本拍什么信息在哪个尺度"？相邻两拍是否同景别同角度同关系？
8. 站位变化是否由本拍 `storyEvents` 支持？没有事件支持的位移是瞬移。
9. 环境空镜拍是否仍用 `landmarks` 和 `camera` 表达了空间拓扑，而不是交一个空计划。

## 十二、失败征兆

- 坐标全合法，但把 `camera` 删掉后没人能说出画面左右。
- 同场景相邻拍的机位在轴线两侧来回跳，越轴没有依据也没被声明。
- 一个拍里 `facingTo` 指向多个方向却没有转向动作支持。
- 所有人都在同一 `depthLayer`，竖屏里挤成一条横线。
- 站位只为填满画面：谁在门口、谁离证据更近、谁被挡住，都不影响剧情。
- 背景人物在切拍后无原因换边；人物为无理由的走动而走动。
- 每句台词都切一个头像近景；景别只跟着情绪词收紧。
- 重要人物一直被前景遮住，但剧情并未利用这种遮挡。
- 只写"俯拍"，下游读成机位高度而不是水平角度，权力关系当场反转。
