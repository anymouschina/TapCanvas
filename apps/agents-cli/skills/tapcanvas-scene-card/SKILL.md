# TapCanvas Scene Card

## 唯一职责

本 Skill 是场景视觉身份、空间设计和场景灯光的唯一方法论来源。其他 Skill 可以识别“需要哪些场景”、提供剧情、时代、人物调度和状态事实，但不得另写场景卡模板、灯光情绪查表、固定 prompt 前后缀、默认模型或 URL 复用规则。

场景卡是无人、可复用的纯空间生产资产；空景仍必须具有明确的叙事功能，不能只有“地点名 + 电影感 + 超高清”。它必须同时完成：

1. **空间身份**：换机位后仍能认出同一地点；
2. **叙事功能**：空间结构确实允许本场戏发生；
3. **材质生态**：建造、使用、维护、损耗和气候留下互相解释的痕迹；
4. **灯光因果**：每束主要光都有来源、方向和作用对象；
5. **连续性**：日夜、天气、实用灯、破坏状态与上一版有可追溯关系；
6. **可执行资产**：落为真实图片节点/素材版本和稳定 ID，供分镜、关键帧与视频复用。

## 资产类型

| `sceneAssetRole` | 用途 | 生成方式 |
|---|---|---|
| `space_anchor` | canonical 空间身份；锁定拓扑、尺度、入口、地标、材质和基准灯光 | 首次建立场景或用户明确重建 |
| `lighting_variant` | 空间不变，只改变可证明的时段、天气、灯具状态或叙事光相 | 必须引用精确 `space_anchor` node/material/version ID，以图生图派生 |
| `state_variant` | 灾损、布置、季节、占用方式等可见场景状态发生变化 | 引用基态或上一状态的精确 ID，只改差量 |

同一变化同时涉及光与物理状态时仍只建一个 variant，并在 `visualStateFacts` 与 `sceneLightingSpec` 中分别记录，禁止同一画面创建两套竞争版本。

## 拓扑图与站位图视觉范式（2026-09-14）

后续拓扑图与站位图的提示词编译必须先读取 [正交建筑剖切与动作调度模板](references/topology-blocking-diagram.md)，以用户提供的 [奶茶店原文](references/topology-blocking-boba-reference.md) 为绘制范式。固定要求为严格 90° 正交顶视、参考空间还原、精细材质、16:9、清晰双语标注与有事实依据的动作/机位关系；场景名称、人物、道具、标语和动作只来自当前任务。该技术图的展示要求优先于下文普通场景卡的非固定画幅/照明建议，且不改变无人空间锚的职责。

## 证据层级

站位/拓扑图默认先生成本场景的无人正交俯视底图，再按结构化坐标叠加角色、走位、机位与轴线。底图保持场景身份、材质和光源；门墙与固定地标服从同一归一化坐标基准，不把透视照片直接当作俯视底图。同一布局/状态可复用一张图，布局变化以新资产表达。

已有场景图时以精确 node/asset ID 图生图派生；没有现成图时依据已确认空间事实原创，不伪称有图片来源。Workflow BeatSheet 的 `blockingPlans[].backgroundPlan` 提交 `assetId/displayName/prompt/negativePrompt/referenceAssetBindings`，独立底图集合负责真实生成，不混入视频参考池。独立工具通过 `backgroundNodeId` 消费底图；给旧图新增版本时同时提交 `sourceDiagramNodeId`，保留旧图和下游引用。禁止传图片 URL。

按以下顺序读取：

1. 用户本轮明确要求；
2. 当前章节/剧本/BeatSheet 的地点、时间、天气、事件和调度事实；
3. 已确认的 style lock、场景素材及精确版本；
4. 上一场景状态与当前项目真实状态；
5. 为可拍性所需的最小自由设计。

内部把设计分成：

- `confirmedFacts`：来源明确，不得改写；
- `designInferences`：从功能、时代、气候、经济与人物使用方式推导；
- `freeDesign`：证据未覆盖时的原创选择，必须与前两层相容。

不得把推断伪装成原文，不得用通用“古风房间 / 赛博街道 / 豪华办公室”母版代替证据。

## 工作流

### 1. 读取并验真

需要读取或操作真实项目、画布、节点与素材库时，只通过 `tapcanvas-api`。场景复用只接受可验真的当前画布 node ID、material asset ID 或精确 version ID；URL、label、prompt、坐标、连线和“看起来像同一个地方”都不能作为 canonical 身份。

先确认：

- canonical `sceneName` 与场景职责；
- 所属时间段、天气、季节和连续性阶段；
- 已有 `space_anchor` / variant 及其精确 ID；
- 当前 project style lock；
- 当前启用图片模型与规格；
- 本场戏需要发生的动作、视线、进出路径和关键物件。

### 2. 建立空间因果核

先回答，再写 prompt：

- 这个空间为何以这种方式建造和使用？
- 谁长期使用、谁维护、谁无权进入？
- 人物从哪里进入、停留、对峙、隐藏或逃离？
- 哪三个地标能让换机位后的观众确认仍在同一地点？
- 哪些材质会因气候、年龄和使用频率呈现不同状态？
- 当前剧情改变了空间什么，又有哪些必须不变？

由此编译 `sceneAnchors`，优先锁定：平面拓扑、尺度关系、固定入口、结构地标、主材质、不可移动大物件与长期使用痕迹。抽象形容词不算锚点。

### 3. 让同项目场景彼此不同

对整组场景做关系设计，至少比较：

- 开放/封闭程度；
- 纵深与层高；
- 入口和视线结构；
- 材质温度与反射性；
- 人为秩序与自然侵入程度；
- 明暗分区和主要光源生态；
- 人物在空间中的权力距离。

差异必须来自地点功能、历史、使用者和剧情压力，不得靠随机摆件、统一雾气、统一霓虹、统一暖窗、统一废墟或“每个场景换一个滤镜”制造假多样性。

### 4. 编译物理灯光合同

情绪不是光源。把“温暖、孤独、危险、神圣、压迫”等意图翻译成可定位的光：

1. **叙事意图**：观众首先看哪里，哪些信息留在暗部；
2. **主光来源**：太阳、天光、窗、门缝、吊灯、台灯、招牌、火焰、车灯等真实或可解释来源；
3. **方向与高度**：画面左/右/后/上、入射角、遮挡关系；
4. **色温关系**：只有有叙事或物理意义时才写暖钨丝、冷月光、中性阴天、荧光偏绿、钠灯等；
5. **光质与对比**：硬/柔、扩散范围、明暗比、阴影边缘和暗部可读性；
6. **空间介质**：雾、尘、雨、烟、水汽只有会接住光且有场景依据时才使用；
7. **材质响应**：木、石、玻璃、金属、湿地、织物如何吸收、漫反射或产生受控高光；
8. **实用灯与背景分离**：画面内灯具是否可见，主体与背景如何分层；
9. **变化**：门打开、天色落下、闪电、灯熄灭等变化必须有触发点、变化过程和保持不变的空间事实；
10. **连续性锁**：同一段落保持光源位置、天气相位、色温关系与实用灯状态，除非剧情明确改变。

不要按“悬疑=顶光、浪漫=逆光”的固定表自动分配。顶光、逆光、侧光、硬光、柔光、体积光等是可选几何手段；选择必须能回到当前空间与叙事因果。避免无来源的棚拍轮廓光和全场均匀平光。

### 5. 静帧与视频分层

场景卡是干净、可复用的静态生产资产：

- 静帧 prompt 写空间、灯光基态与可见材质，不写镜头运动；
- `lighting_variant` 可写某一明确光相，但不模拟整段动画变化；
- 闪烁、扫光、日落推进等时间变化写入 `transition`，供后续视频 prompt 使用；
- 胶片颗粒、呼吸感运镜和动态空气效果属于视频/后期层，不得为了“去 AI 味”污染场景卡；
- 真人、动画、插画、定格等媒介只服从用户要求与项目 style lock，不得默认真人写实。

### 6. 首轮生图：空间职责与洁净材质

以下方法在一键成片的素材创作节点编译首轮图片 prompt 时执行，也适用于独立场景卡生成。不能把“先出含人物/颗粒的图，再去人去噪”作为默认生产步骤。

**无人空间是资产职责，不是剧情删改。** 所有场景卡及灯光/状态版本均不出现人物、人群、人体局部、倒影或剪影。地点身份只包含稳定的空间事实；人物占用、拥挤程度、排队、交战、表演、姿态和动态过程留在 BeatSheet 的事件与对象状态中，由现有 clip writer 写进视频提示词。不要把这些事实删除，也不要为补人物另建生成流程。人多不意味着空间狭窄、建筑破旧或环境脏乱，禁止用无来源的空间改造替代人群语义。

一键成片作者在同一次响应中分别编译剧情与参考资产，不能把 `visualIntent/startState/storyEvents` 的整句内容直接复制进场景 `prompt`、`negativePrompt`、`identityAnchors` 或 `prohibitedDrift`。逐项复核上述四个字段及 canonical 名称：无人时仍成立的空间、固定物件、材质和光照才属于场景资产；依赖人物在场的内容保留到原 Beat。负向限制不能禁止无人状态。项目风格中的人物/表演内容也不改变该职责。该语义自检由资产作者在提交前完成，不由后端关键词、正则或评分门禁替代。

一键成片 `assetPlans` 的结构按 role 区分：`scene://`（以及协议中的 environment 角色）提交 `sceneCard={sceneProfileVersion:"scene-card/v1",sceneAssetRole:"space_anchor",sceneOccupancy:"none",sceneLightingSpec:{...}}`，灯光完整字段见下方合同；`identityAnchors` 仅记录空间锚，`prohibitedDrift` 仅记录空间不变量，宿主逐字投影为 `sceneAnchors/prohibitedSceneDrift`。场景项不提交 `identityBoardSpec`，人物四视图只属于 character 项。schema 不符沿现有结构化输出修复链纠正，不能靠执行层补一句无人要求代替这份合同。

**从剧情提取空间，不复制表演。** 人物调度用于推导空地尺度、入口、通道、遮挡、视线和固定物件落位；最终 prompt 只描述这些空间事实。例如“竹林围绕交战者”应编译成“竹丛围合中央空地，地面通道连续可读”，不保留交战者、站位、服装或动作。基准空间与战损状态分别表达；状态版可保留有来源的断竹、裂痕等静态结果，不把冲击波、人物能力或飞散过程混入基准卡。

**按资产职责消费项目画风。** Agent 从真实 style lock 中选取适用于环境的媒介、材质、配色和光照，保持项目风格身份。例如“人物水墨剪纸、环境三维渲染”在场景卡中只落实环境三维材质与对应配色；人物纸边、服饰、脸部笔触、打斗能量和视频运镜不转移到环境。共享风格文本可能随请求附加，因此可执行 prompt 本身须明确：本图只呈现无人环境，项目人物/动作说明不代表本图应绘制人物或特效。不得依赖 negativePrompt 单独承担这一语义，也不得交给 Hono/Web 以关键词删除、正则过滤或固定模板代替 Agent 编译。

**洁净度来自材质和光照设计。** 描述竹节、叶缘、石纹等真实结构与适度细节，同时要求雾区、天空、平滑表面和暗部具有连续明暗过渡。避免为了“丰富/电影感/去 AI 味”增加随机颗粒、彩噪、全局纸纹、脏污碎纹、锐化光晕或无来源发光粒子。保留有事实依据的磨损、自然纹理和项目明确选择的笔触，不以去噪为由抹平细节、改写媒介、压成塑料表面或用浓雾与模糊遮掩问题。物理雾气与随机噪点不是同一种东西。

**已选 GPT Image 2 时。** 将上述空间与洁净材质要求直接编入第一次提交的 prompt，表达需要的正向画面与具体排除项，不堆叠画质咒语。模型、尺寸、比例沿用本轮冻结合同；当前工具确实暴露质量选项且授权预算允许时可选 high，但不得把 high/2K 当作去噪保证、擅自升级规格或编造 denoise strength、采样步数等参数。不得默认追加一次付费编辑。其他模型同样遵守纯场景职责，模型参数仅依真实能力选择。

### 7. 编译节点合同

新场景资产统一写：

```json
{
  "kind": "image",
  "referenceType": "scene",
  "sceneName": "<canonical scene name>",
  "sceneAssetRole": "space_anchor | lighting_variant | state_variant",
  "sceneProfileVersion": "scene-card/v1",
  "sceneAnchors": ["<可见且可验证的空间身份事实>"],
  "prohibitedSceneDrift": ["<有事实依据的不可偏移项>"],
  "sceneLightingSpec": {
    "version": "scene-lighting/v1",
    "narrativeIntent": "<观众应先读到什么，以及暗部保留什么>",
    "keySource": "<物理来源>",
    "direction": "<方向、高度与遮挡>",
    "colorTemperature": "<有意义的色温关系>",
    "lightQuality": "<硬柔、扩散、对比与暗部可读性>",
    "shadowBehavior": "<阴影方向、边缘与落点>",
    "atmosphereInteraction": "<介质如何接光；无依据时写 none>",
    "reflectiveBehavior": "<关键材质的反射/高光行为>",
    "practicalSources": ["<画内可见或可推断灯具>"],
    "continuityLocks": ["<跨镜必须保持的灯光状态>"],
    "transition": {
      "trigger": "<变化触发；无变化时省略整个对象>",
      "change": "<光如何变化>",
      "invariants": ["<变化中保持不变的事实>"]
    }
  },
  "prompt": "<本场景独有的可执行图片提示词>",
  "referenceImageNodeIds": ["<当前画布 scene ID，若有>"],
  "referenceAssetIds": ["<素材或精确版本 ID，若有>"],
  "approvalStatus": "needs_confirmation",
  "imageModel": "<enabledImageModels 中选定的精确 modelKey>",
  "imageSize": "<该模型实时支持的精确规格>"
}
```

`space_anchor` 不出现人物；它可包含人物即将使用的固定家具、门、通道与叙事道具位置。人物站位、动作、神态属于分镜/关键帧，不写进 canonical 空间卡。会被拿取、交接、操作、损坏、变形或跨场景复用的独立物体必须交给 `tapcanvas-prop-card` 建立 `prop-card/v1`；场景卡只记录它在空间中的固定落位，不复制其身份、结构或状态合同。

这是生成约束，不只是验收建议：所有 `space_anchor` 的可执行图片 prompt 必须明确写成纯空间参考图，并包含“画面中无人、无人物、无群演、无路人、无人体局部、无人物倒影/剪影”等同义的排除事实。场景中即使发生过人物事件，也只能通过被使用过的空间痕迹、固定道具落位和可解释的环境状态表达；不得把剧情中的人物、人物站位、动作或肖像带入场景卡。`lighting_variant` 与 `state_variant` 继承同一条人物排除约束，人物可见的合成画面不属于场景卡；场景卡没有人物可见例外。

`lighting_variant` 和 `state_variant` 必须以 `referenceImageNodeIds`、`referenceAssetIds` 或 `referenceAssetBindings(role="layout"|"content")` 引用精确基态/上一状态 ID。禁止把 URL 写进 prompt、`referenceImages`、`anchorBindings` 或 `assetInputs`，禁止只写“保持同一场景”却不给引用 ID。

模型和规格来自用户显式选择、账号生成偏好与实时 `enabledImageModels`。不存在固定 gpt-image-2、固定 2K 或固定 16:9 默认；无精确可执行项时如实失败，不自动换模型。

### 8. 同链生成与对账

具备生图权限时：先写完整节点合同，再调用图片生成工具，任务受理后保留 running 节点与 task ID，通过 reconcile 收集结果；不重复付费。只有编排/占位权限时，落完整 `needs_confirmation` 节点并明确尚未生成，不能把 prompt 当真实场景资产。

生成后以真实 node/asset/version ID 对账。已产出资产不得因后续审查被回滚、覆盖或丢弃；问题以诊断和新版本追加。

### 9. 去 AI 味与提交前自检

检查首稿：

- 空间是否能解释本场戏的调度，而非“好看的背景”；
- 是否存在至少三个换机位仍可识别的场景锚；
- 材质、磨损与摆放是否来自使用因果，而非随机细节；
- 灯光是否有物理来源、方向、色温关系、阴影和材质响应；
- 是否出现无来源轮廓光、全亮平光、统一体积雾、统一霓虹或抽象“电影感”；
- 同项目场景是否在拓扑、尺度、材质与灯光生态上真正不同；
- variant 是否只改状态差量并绑定精确上游 ID；
- 是否误把人物、镜头运动或视频质感写进空间锚。
- 结合将随请求附加的真实项目风格，最终 prompt 是否仍明确无人；是否把人物专属媒介和战斗特效误当作环境材质；
- 平滑区域与暗部是否要求干净连续，同时保留真实材质；基态与战损/灯光状态是否互相矛盾；
- 当前工作流输出 schema 允许的场景合同字段是否随 prompt 一起提交，不能只给场景标题和散装描述；schema 无法承载时记录具体协议缺口，不伪称已经持久化空间锚。

不满足时在同一 agents-cli 执行链内修订 prompt、锚点和灯光合同，再提交或交付；自检是创作责任，不得实现为 Hono/Web 的语义质量门禁。

自检发生在首次付费图片提交之前，只修订当前创作输出，不增加独立审查轮次、评分门票或固定最低字数。供应商受理后保留任务与全部产物；后续发现问题仅追加诊断，修订图须遵守已有授权，不自动重绘或把已生成资产判为不可交付。

## 明确删除的旧方法

- 不再使用世界观关键词表、正则或固定时代枚举路由场景 prompt。
- 不再使用“兼容模式 / 借鉴模式”两套固定前缀。
- 不再要求先有 style reference 才允许生成。
- 不再默认 gpt-image-2、2K、16:9、写实、电影感、雾气、颗粒或某一种光型。
- 不再把历史 scene URL 直接复制成新场景卡；只认精确 ID。
- 不再由 `tapcanvas-generate-scene-references`、storyboard 或 video writer 维护平行场景设计与灯光模板。
- 不使用禁词命中、最低字数或审查分数阻止生成、持久化或交付。

## 完成标准

只有同时满足以下事实才可声称完成：

- 场景节点已按授权范围创建或真实生成；
- `referenceType=scene`、canonical `sceneName`、`sceneAssetRole`、`sceneProfileVersion=scene-card/v1` 完整；
- 空间锚与灯光合同来自当前场景事实；
- variant 绑定精确基态/上一状态 ID；
- 模型与规格来自实时能力或显式偏好；
- 结果落点、状态和真实资产证据与用户目标一致。

一键成片的场景 authoring 分支只提交 `role/identityAnchors/prohibitedDrift/sceneCard`。可执行空间描述写入 `sceneCard.spacePrompt`，同图排除项写入 `sceneCard.negativePrompt`；不提交通用顶层 `prompt/negativePrompt`，以免剧情表演描述直接流入生图。投影器仅把这两个已创作字段逐字映射为图片执行字段，并校验往后各跳仍与原字段相同，不生成或改写语义。场景 Skill 上文的独立画布节点 `prompt` 仍表示这份空间描述在节点上的落点。
